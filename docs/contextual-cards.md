# Contextual cards integration

Successful current Run or Preview with a public preview action automatically prepares a reusable Preview card. The wrapper uses the approved `RuntimeIdentity` retained at conversation admission. It returns `app_card={status: prepared, view: ...}` or `app_card={status: unavailable, code: ...}` separately from native success, receipt, claim, outcomes and public action. Known preparation codes are `card_capacity_reached`, `card_stale`, `card_state_malformed` and `claim_owner_conflict`. Other preparation exceptions become `app_card_preparation_failed`, without exception text. Cancellation propagates. Failed, denied and non-effect calls do not prepare a card. Consumed-card finalization retains its separate `card` result.

The agent immediately calls public `desktop_preview` with the current `preview_action.arguments` in the originating turn, then includes `app_card.view.directive` in its reply by default. Backend preparation does not insert a transcript directive or render a widget. Public open acknowledgement does not prove mounted content or fresh pixels. After an external build, ordinary approved Preview supplies the same handoff. A failed rebuild leaves the previous version; it supplies no updated pixels. Setup automation and full lifecycle qualification remain outside this change.

`ios_iteration(action="card", card_action="run"|"preview", ...exact target...)` issues a card. `action="card", card_id=<32 lowercase hexadecimal characters>` resolves it with the current exact target. Issuing and resolving require authenticated `tool_execution` metadata and never request native approval. The returned file directive uses the builtin host-owned `::preview{file=...}` contribution. The only artifact effect is an HTML file under the registration's `data_dir/cards`; there is no caller-selected widget path.

`data-hermes-send` contains a bounded opaque lookup prompt. Its containing chat supplies the authenticated host origin. Neither directive attributes, a delivery acknowledgement, handler keyword arguments nor focus can supply authority. A failed delivery produces no tool invocation and no consumption. The agent resolves the ID and passes the returned action and target arguments to ordinary `ios_iteration`, including `card_id`. Each invocation requires normal run/preview approval. Ordinary chat without a card remains supported. Dashboard REST still denies run, preview and card actions.

The host adapter uses `session_id`, optional `task_id` and `turn_id`, and required `tool_call_id` from the real pre-tool/tool-execution metadata. The profile comes from registration. The composed consumption request ID is canonical JSON of `[profile, session_id, task_id, turn_id, tool_call_id]`, using empty strings for omitted task/turn fields as defined by `RequestKey`. Model-supplied identity, approval, context, argv and widget paths are rejected. Approval disclosure also binds the optional card ID, so it cannot be swapped after disclosure.

Records live in the existing `native-runs.json` store under `cards`, using its file lock and atomic durable writer. A strict versioned loader validates every card, full target identity, generation and bounded result/history shape; malformed state is never interpreted as an empty registry. IDs are backend-generated. A Run issue supersedes any pending or consumed Run card in the same authenticated session, exact full target and action slot. Superseded IDs return `card_not_found` and cannot execute. A Preview issue returns the existing scoped card ID and widget path, including after consumption. Other sessions, targets and actions keep their records. The registry has a cap of 128 current slots per store; a new slot at capacity fails without mutation. Reusing Preview or replacing Run in an existing slot remains available at capacity. Old superseded Run HTML files may remain but their IDs are inert. Native history, repair budgets and resource obligations are unchanged.

Run binds the full `RuntimeIdentity`, target fingerprint, trusted Git source fingerprint, executable build-input fingerprint, action revision (`contextual-run-v1`) and issue-time device claim generation. Source/build revisions are recomputed outside the global store lock, including consumption under the device lease. All original Run revision and consumption checks remain. A consumed Run result remains readable after edits without admitting execution. Run cannot be retried through its consumed ID, even if no operation was verified.

Preview binds the full target, session/profile, current owner and action revision (`contextual-preview-v1`). It checks the freshly disclosed claim generation both before preflight and at consumption under the device lease. A consumed Preview also requires any current device claim's full target to match, even when the owner is unchanged. It cannot switch the current claim to another project/app. With no current claim, an interrupted first admission can retry; there is no other current target to displace. A fresh pending card retains explicit initial-target selection. Issue-time generation is history rather than reusable authority, so the card survives its own first claim from generation 0 to 1. Preview executes neither source nor build inputs, so changes to those revisions do not invalidate it. Stored fingerprints remain actual issue-time history, not observations of a new build. Existing Preview resolve, check, consume and reissue never call either fingerprint function. New Preview and Run issuance compute genuine fingerprints outside the store lock. Issuance checks for a matching Preview first and rechecks under the write lock after fingerprinting, so a concurrent matching insertion wins. A stale action revision refuses reuse rather than replacing the ID. A different session/profile sees `card_not_found`. A changed target, action, action revision or disclosed generation is refused. Current foreign ownership is refused.

After normal host approval is consumed, the controller's device lease encloses the short store transaction applying the pure card reducer. The store lock ends before ownership admission and native work. Card preview performs ordinary preflight and a read-only booted-simulator query before consumption or claim admission. Preflight refusal leaves the card and claim unchanged. Consumption, claim admission and stock ensure then share one device lease. Preview never builds, boots, installs, launches or resets the app. It asks the existing controller to reconcile/reuse the server and returns the ordinary public preview-open action. The agent executes that action to reopen a closed Browser URL or reveal the already visible preview. No separate server or sender is introduced. Run continues through its existing handler, operation allocation, dispatcher and result reporter.

Consumption remains durable. Run moves from pending to consumed once. Preview stays consumed after its first activation but a different authenticated invocation can reactivate it through fresh normal host approval. The latest request identity fences completion. A replay of the current request cannot execute again. An older request redelivered after another activation may repeat the idempotent preview effect only with fresh approval; bounded state does not promise permanent exactly-once Preview calls. A late finish from a superseded request cannot replace the current result or history. Approval denial never reaches consumption and never fabricates success.

Version 1 cards load as version 2 in memory and persist on the next card mutation. Migration preserves a consumed Preview's original request identity, generation, operation state and latest result in an immutable `preview_history.legacy_consumption` snapshot before repurposing the current request field. Constant-size `last_success` and `last_failure` evidence each retain their authenticated request identity, generation and result. Only a success with an actual operation ID becomes historical operation success. New failure or unknown completion never borrows an earlier receipt. Consumption clears the latest result to outcome unknown while retaining bounded history. A failed or crashed Preview remains retriable through normal controller checks and clears no unknown resource obligation. Native attempt history, budgets and lifecycle proofs are untouched. Successful Preview records the actual controller lease operation ID, not a native build receipt. Older version 1 readers refuse the version 2 registry.

The returned view includes `reusable`, `revision_scope`, `latest_result` and `preview_history`. Preview `status="consumed"` describes activation history, not exhausted Run authority. Its enabled Open app button says each use is reviewed in chat. The compact card shows the project-derived app label, scheme and runtime, with one primary button. Full UDID, project path, operation diagnostics and unknown pixels appear in closed Details. Pending Preview says Ready to open; history says Last Preview operation succeeded, failed or outcome unknown. These are historical operation results, not current app state or browser-open proof. Run remains disabled after consumption. Resolving an existing Preview rewrites its same HTML path when needed, including a legacy disabled file. Widget publication reloads the authoritative row under the existing store lock; an old caller cannot publish its stale snapshot after a newer result. Small file writes are serialized, with no native work under that lock. A temporary file and atomic replacement preserve complete HTML on write failure. Store mutation commits before publication, so artifact failure does not undo consumption. `card_status_error` and the existing `card_replay_allowed=false` report a finalization failure for that invocation; they do not retire a reusable Preview. Visible pixels remain explicitly unknown until separately observed.

Source integration tests instantiate production registration, hooks, middleware, controller locking, authority and disk stores. They replace native dispatch, simulator queries, prerequisites and stock process effects. Synthetic contexts stand in for the host. They do not prove installed host authentication, widget rendering/Send delivery, approval UI, simulator state or fresh pixels. Parent acceptance must resolve the original card, close only its Browser URL, reopen through that same card and then reveal while visible, with the same app/URL and one server. A replacement card does not satisfy that acceptance.
